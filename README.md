# ShelfCart

**Shop any image on the web, change the item to how you want it, buy the real thing.**

Give ShelfCart a picture: right-click any image in Chrome, capture the page you are on, paste a screenshot, drop a file,
or pan a camera. It marks what can be bought in the picture and finds each item as a real product in Shopify's catalog
across all merchants (Shop MCP, https://shop.dev), with the store name, live price, stock and discount. Then you can
change an item ("make it corduroy", or a colour the store really sells): real products for the new version appear in
about a second, and the picture is redrawn with only that item changed so you can see it in place. You choose the
listings, you press the button that builds the carts, and you pay on Shopify's own checkout page. The app never pays.

Built on Nov 21, 2026, during the Gemini 4 hackathon (problem statement "Element 119": an image is the input, there is
no search box; Shopify bonus track: catalog search, carts and checkout are real Shop MCP calls with no API key).

## Find it, compare it, buy it

1. **Find it.** The image is the page. Each found item gets a numbered yellow marker on the picture and a row beside it.
2. **Compare it.** Opening an item shows real listings from different Shopify stores: photo, title, store name, live
   price, the compare-at price and percent off when the merchant has a discount, in stock or sold out, rating. Each
   item is labelled **Exact**, **Exact?** (probably, not pre-selected), **Similar** (with one line on how it differs)
   or **Nothing close**, with the model that decided.
3. **Change it.** Three kinds of variation, in this order:
   - **Real options of the matched listing.** If the listing has options in the catalog (colour, size, pack), they
     are shown as chips with the merchant's own swatch photos and sold-out values struck through ("The closest listing,
     from Kinwell Furniture, really comes in: Black and white, Charcoal, Teddy brown"). Choosing one resolves the exact
     variant with its own price and stock in about 0.3 s. For a visual option the picture is also redrawn, using the
     merchant's photo of that variant as the reference.
   - **Ideas from Gemini 4 Hydrogen.** Four variations that suit the scene (two colours, a material, a shape).
   - **Your own words.** A text box: "make it corduroy", "in navy", "with wooden legs".
   For an idea or your own words, two things start at once: a Shopify search for the new version, ranked by Decision 1
   in under a second and then judged by Neon (always labelled Similar, because the new version is imagined), and the
   redraw, which replaces the picture after 10 to 16 s. A switch flips between **Original** and **Preview**. Every
   redraw carries the label "Generated preview" on the picture and "Preview generated by Gemini, the real product may
   differ" under it. Redraws are cached per image, item and variation.
4. **Buy it.** The bar at the bottom says what will happen in plain words ("2 items, $1,845.19. 2 carts, 2 stores:
   Shopify needs one cart per store"). **Build 2 carts** creates real carts. Each cart then has **Check out with Shop
   Pay**, which creates a checkout session and opens Shopify's own checkout page (shop.app) in a new tab.

## Which model does which job

| Step | Who | Job |
|---|---|---|
| See | `gemini-4-hydrogen` | Reads the image (or 1 to 5 camera frames). Lists each purchasable item once: brand, name, variant, size, box, confidence, search query. Ignores app chrome, faces and captions. |
| Suggest | `gemini-4-hydrogen` | For an opened item, proposes 4 variations that are really sold and suit the scene, each with an edit instruction and a search query (`app/remix.py: suggest`). About 6 to 8 s, loaded when the item is opened, cached. |
| Search | Shop MCP `search_catalog` | Shopify's Global Catalog across all merchants, per item and per variation. Real, no API key. About 0.3 s. |
| Exact match, fast | `gemini-decision-1` | Gets the item crop and the listings. One `choice` ranks them, one `noul` per listing answers "same product?", one `noul` "is the label readable?". About 1 s per item, calibrated, so it decides what is safe to pre-select. For a variation it answers "does this listing have the change that was asked for?" per listing, which orders the cards at once. |
| Similar items, careful | `gemini-4-neon` | Second look whenever Decision 1 has no sure exact match (the normal case for clothes, furniture, decor). Compares the crop with the store photos, checks pack size and variant, then confirms an exact listing, or picks the closest similar one and says in one line how it differs, or says nothing is close. For a variation it judges the listings against the imagined version. 7 to 12 s, in parallel. |
| Real options | Shop MCP `get_product` | The matched listing's real options with availability and swatches, and the exact variant for a selection. |
| Redraw | `gemini-nano-banana-2.1` | Redraws the picture with only that item changed (`app/remix.py: render`). The server checks that the rest of the picture was kept (same proportions, pixels outside the item's box nearly unchanged), retries once, and shows no preview rather than a recomposed scene. |
| Cart | Shop MCP `create_cart` | One real cart per merchant, only after the person presses the build button. |
| Checkout | Shop MCP `create_checkout` | Only on a second press. Returns Shopify's review-and-pay page. `complete_checkout` is never called. |

## How a person stays in control

- Only confident exact matches are pre-selected: Decision 1's choice and yes/no agree, P(same product) >= 0.8,
  Hydrogen confidence >= 0.6, P(label readable) >= 0.6; or Neon confirms an exact listing with matching quantity.
  The row then says "In selection" and one press removes it.
- Similar items and everything found for a variation are never pre-selected. Similar is always labelled Similar, with
  the difference spelled out.
- Store name, live price, discount and stock are on screen before anything is added.
- No cart exists until the person presses the build button, which states the number of carts and stores. Checkout is a
  second, separate press per cart and only opens Shopify's own page. The app never completes a checkout and never sees
  payment details.
- A redraw is labelled as a generated preview on the picture itself and under it, and the original is one press away.
- If two accepted listings exist and one is from a store already in the selection, that one is used (Decision 1
  matches only), because Shopify needs one checkout per store.
- The server only accepts POSTs from its own page or a browser extension, not from other websites.

## Sign in with Shop (optional)

Under the carts there is "sign in with Shop". It uses Shop's OAuth device flow with the public client ID that
Shop publishes for prototypes (https://shop.dev/docs/authentication): no key, no secret, no registration. The server
asks Shop for a code, the page shows a link to Shop's own approval page, and the person approves there. The token is
kept in the server's memory only (never on disk, never sent to the page, never logged) and is added to Shop MCP calls,
so searches use the shopper's Shop preferences and Shopify's checkout can offer their saved Shop Pay details.
Everything works without it. An app that is distributed would need its own registered client (Shopify Dev Dashboard,
`personal_agent` scope). Tested: the request for a code and link, cancel and sign-out. Not tested: the approval itself
and signed-in calls, which need a person with a Shop account.

## Chrome extension

`extension/` is a Manifest V3 extension (see `extension/README.md` for loading it). Right-click any image and choose
**Shop this image**, or click the toolbar button to capture the visible tab. Chrome's side panel opens beside the page
with this app working on that image. The extension is thin: its service worker fetches the image bytes (falling back to
a capture of the visible tab when the site refuses), posts them to `POST /api/image`, and the panel shows
`/panel?scan=<id>` from this server in a frame. If the server is not running the panel says so, shows the start
command and continues by itself once the server is up.

## Run

```
cd ~/dev/g4-shelf
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp ~/dev/bugrepro/.env .env        # GEMINI_API_KEY; .env is git-ignored
.venv/bin/uvicorn app.server:app --port 8202
```

Open http://localhost:8202 and press Cmd+V with a screenshot on the clipboard (on a Mac, Ctrl+Shift+Cmd+4 copies a
screenshot to the clipboard), or drop an image anywhere on the page, or choose a file. The scan starts by itself.
"Use the camera instead" pans a camera for 4 seconds (needs `localhost` or HTTPS).

The page is plain HTML, CSS and JS with no build step: `web/index.html`, `web/app.css`, `web/app.js`. It is one layout
that works from a 360 px side panel to a wide window, in light and dark, with visible keyboard focus and reduced
motion respected.

Endpoints:

- `POST /api/image` (raw image bytes, or `{data_url}`) stores an image and returns `{id}`; `GET /api/image/{id}`.
- `POST /api/scan/stream` (`{image_ids}`) streams one JSON object per line: `items`, then `match` per item, `matched`,
  `review` per item (Neon), `done` with timings. `POST /api/scan` and `/api/review` are the older one-shot calls that
  `tests/eval.py` and `tests/run_e2e.py` use.
- `POST /api/remix/suggest`, `/api/remix/match`, `/api/remix/review`, `/api/remix/render`; `GET /api/render/{key}`.
- `POST /api/product` (`{product_id, selected}`): real options and the variant for a selection.
- `POST /api/cart`, `POST /api/checkout`, `GET /api/eval`, `GET /api/health`, `GET /panel`.
- `GET /api/shop/status`, `POST /api/shop/signin`, `POST /api/shop/signout`.

Measured on Nov 21, 2026 on a living-room screenshot with 11 items (page timings from `tests/ui_test.py`):
first items on the picture after 7 to 8 s, first matches 1 s later, all matches by 9 to 10 s, all of Neon's second
looks by 19 to 24 s. For a variation: real products after 0.6 to 0.9 s, the redraw after 10 to 16 s, Neon's pick after
8 to 18 s. A real option resolves in 0.3 s.

## What the Shopify catalog exposes (checked Nov 21, 2026)

- `search_catalog` returns one featured variant per product with `price`, `list_price` (the compare-at price, present
  only when discounted), `availability.available`, the variant's own option values, `seller` (name, domain, url),
  rating, and the product's `options` as names and value labels. It does not return the other variants.
- `get_product` with `selected: [{name, label}]` returns the exact variant for that selection (id, price, stock,
  photo) and, per option value, `available`, `exists` and a `swatch.image_url` where the merchant has one. About 0.2 s.
- Nothing in the response says how large a store is, so the app cannot prefer a small independent store over a large
  brand by data. It shows the store name on every listing and leaves that choice to the person.

## Does it work

`tests/eval.py` compares two systems on 7 images in `data/test/` (5 photos: bathroom shelf, bag, desk, cafe table,
hot sauce wall; 2 synthetic screenshots: a living room post and an outfit video frame) against a hand-written answer
key of 39 items: 19 branded items where a correct exact listing can be named (brand + product type, variant and
single vs multi-pack where visible) and 20 unbranded items where only a similar item exists.

- **Full pipeline:** Hydrogen, Shopify search, Decision 1 gate, Neon second look.
- **Baseline:** one `gemini-4-hydrogen` call that names the products, then the first Shopify search result for each,
  straight into the selection. No Decision gate, no Neon.

Run of Nov 21, 2026, each system run twice, totals over both runs (saved in `data/eval.json`, shown on the page):

| | Items found | Correct exact, pre-selected | Wrong pre-selected (the costly error) | Correctly held back | Held back, top listing was right | Similar item acceptable | Seconds per image |
|---|---|---|---|---|---|---|---|
| Full pipeline | 78 / 78 | 29 / 38 | 0 | 2 | 7 | 39 of 39 offered (40 possible) | 29.0 |
| Baseline | 78 / 78 | 26 / 38 | 12 | 0 | 0 | 38 of 40 offered | 5.7 |

Per run: pipeline 14 then 15 correct, 0 and 0 wrong; baseline 14 then 12 correct, 5 then 7 wrong.

Where the baseline wins or ties:

- **Speed.** 5.7 s against 29 s per image (measured with 3 images running at once). On the page the first results
  appear after Hydrogen and Decision 1 (8 to 12 s) and Neon's answers fill in over the next 10 to 20 s.
- **Finding items.** Both found every keyed item. Detection is not where the pipeline adds anything.
- **Unbranded items.** The first search result was an acceptable similar item almost as often (38 of 40 against
  39 of 39). By this crude measure Neon's pick is not better than the first result; what the pipeline adds there is
  the stated difference and that the item is a suggestion, not something already selected.
- **Fewer taps.** The pipeline held back 7 branded items whose top listing was right, so the person has to tap them.

What the numbers hide:

- Small sample: 7 images, 2 of them synthetic screenshots, keyed by one person on the day.
- A listing is judged by keywords in its title and seller name, not by a person opening it. Checked by hand, about 3
  of the baseline's 12 wrong picks were right but spelled differently ("Moisturising", "Post It", a Hydro Flask listing
  without the brand in the title), so the real figure is nearer 9. In the other direction, 6 of the pipeline's 7
  "held back, was right" are cases where Neon flagged a real size difference (Heinz 20 oz against a 14 oz bottle,
  The Ordinary 60 ml against 30 ml, Orbit 12-pack) that the keyword scorer cannot see.
- For unbranded items "acceptable" only means the right type of thing with the main attribute (a green sofa, a jute
  rug). Nobody checked that it really looks alike.
- The key and scorer were corrected once after a first run (brand taken from the seller name, "RX Bar" spelling,
  Cholula flavours). The first run had scored 5 pipeline picks and 16 baseline picks as wrong; most were scorer misses.
- Items found outside the answer key are not scored: 23 for the pipeline (none pre-selected), 39 for the baseline
  (all pre-selected, including a laptop, a duffel bag and greeting cards).

Known failure cases:

- **Dense shelves.** A wall of about 300 hot sauce bottles yields only the few items with large labels; the scan is
  capped at 12 items and small labels are not readable at 1280 px.
- **Generic unbranded items.** A mug, a notebook, a coat: there is no exact listing, so the result is a look-alike
  picked from 6 search results. In one run nothing was offered for the round sunglasses, in another for wired earbuds.
- **Pack sizes.** A single can or bar often only has multi-pack listings (KIND 12-bar box, Orbit 12-pack). Neon says
  so in words and holds it back, but cannot find a single unit that is not in the search results. The cart also uses
  the listing's default variant.
- **One cart per merchant.** The best listings usually come from different stores, so 5 items can mean 5 carts and
  5 shipping fees.
- **Run-to-run variance.** Hydrogen names and boxes items a little differently each run, so the item count changes
  (11 against 12 extra items between the two runs) and a match can flip between Exact and Similar (Post-it Notes did).
- **Speed.** Each Neon second look takes 7 to 12 s and now and then much longer; a screenshot with 11 unbranded
  items settled in 23 s on a good run and 45 s on a bad one (one Neon call timed out and the item stayed "Nothing close").

## Shopify calls (verified Nov 21 2026, no key, no sign-in)

All are stateless JSON-RPC POSTs to `https://mcp.shop.com/` (no `/mcp` path, no `initialize`). See `app/shopify.py`.

Headers: `Content-Type: application/json`, `Accept: application/json, text/event-stream`,
`MCP-Protocol-Version: 2026-07-28`, `Mcp-Method: tools/call`, `Mcp-Name: <tool>`.

Body: `{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"<tool>","arguments":{...},"_meta":{
"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientInfo":{"name":"shelfcart","version":"0.1.0"},
"io.modelcontextprotocol/clientCapabilities":{}}}}`. The result is in `result.structuredContent`.

- `search_catalog` arguments: `{"catalog":{"query":"...","context":{"address_country":"US","currency":"USD"},"filters":{"ships_to":{"country":"US"}},"pagination":{"limit":6}}}`.
  Each product has `variants[0]` with `id`, `price.amount` (minor units), `seller.domain`, `url`, `checkout_url`.
- `create_cart` arguments: `{"shop":"<seller.domain>","cart":{"line_items":[{"item":{"id":"gid://shopify/ProductVariant/..."},"quantity":1}],"context":{...}},"meta":{"idempotency-key":"<uuid>"}}`.
  Returns `id`, `totals`, `continue_url` (the merchant's cart page).
- `create_checkout` arguments: `{"shop":"...","checkout":{"cart_id":"<cart id>","line_items":[],"context":{...}},"meta":{"idempotency-key":"<uuid>"}}`.
  Returns `status: requires_escalation`, tax in `totals`, `continue_url` (a shop.app review-and-pay page).

`tools/list` on the same URL returns the full schemas.

## Tests

- `tests/eval.py [--runs N]` is the baseline comparison above. It writes `data/eval.json`, which the page shows.
- `tests/run_e2e.py image.jpg [--pan N] [--cart]` runs the pipeline through the server and prints every candidate with its scores.
- `tests/ui_test.py image out_prefix [--width 400] [--dark] [--how paste|drop|file] [--wish "..."] [--option] [--cart]` drives the
  page in headless Chromium (needs playwright, e.g. `~/dev/bugrepro/.venv/bin/python`) and screenshots every stage:
  reading, items, matches, a variation's products, the redraw, carts, the checkout hand-off (never completed).
- `tests/remix_test.py image.jpg` is the same path through the API only, with the time of each stage.
- `tests/ext_test.py image.jpg out_prefix` loads the extension in Chromium and tests the service worker, the capture
  fallback, the panel page and the server-down message.
- `tests/gen_image.py` makes synthetic test images with `gemini-nano-banana-2.1`; `tests/bench_detect.py` compares detection settings.

The test images live in `data/test/` and are not in git (about 700 KB each); `data/eval.json` is.

## Known limits

- Hydrogen takes 6 to 11 s for one image; search plus Decision 1 about 1.5 s for all items in parallel; each Neon
  second look usually 7 to 12 s, sometimes 30 s or more. They run in parallel; a second call is started for an item
  after 14 s and the first answer wins; after 30 s the item keeps Decision 1's verdict.
- A similar item is chosen from only 6 search results per item, so "closest" means closest of those six.
- The cart uses the listing's featured variant unless the person picks another real option under "Change it".
- Usually one cart per item, because the best listings come from different merchants.
- Anonymous Shop MCP calls have the lowest rate limits; no 429 was seen in testing, the client retries twice.
- Paste and drop were tested in headless Chromium with synthetic events and the upload path end to end; live camera
  capture was written but not tested on a machine with a camera.
- The redraw is a generated picture. It usually keeps the scene (1 of 2 in testing before the instruction was
  tightened, 8 of 8 after); when it does not, the server retries once and then shows no preview. Small items (a pair of
  sunglasses) change little. Variations of one item are not combined with variations of another in one picture.
- A variation's products are always Similar: they are matched to an imagined version, from 6 search results.
- A typed wish is turned into a search query by dropping its lead-in words ("make it", "in"), with no model call, so
  an unusual phrasing gives a poor query.
- Real options are offered for the matched (first) listing only, at most 12 values per option.
- The extension was tested in Playwright's Chromium by calling the service worker's handlers. The real right-click
  menu entry and Chrome opening the side panel on a click need a person; `sidePanel.open` refuses to run without a
  real click, as expected.
- Sign in with Shop: the approval step and signed-in calls are untested. The access token is not refreshed; when it
  expires the app goes back to anonymous calls.
- Uploaded images and redraws are kept in `data/uploads` and `data/renders` (the newest 120 of each).
